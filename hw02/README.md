# Домашнее задание №2. Детальное хранилище для «Аптеки 108»

## Important notice

1. **Задание выполняется и оценивается индивидуально или в группах до 4 человек.**
   Если вы используете код из открытых источников (репозитории ваших
   одногруппников таковыми не считаются) — указывайте ссылки на них.
   Ведите лог источников в `docs/sources.md`. Находить готовые рецепты
   в интернете — хорошо, списывать — плохо.
2. **LLM пользоваться можно и нужно** — как вы и будете делать на работе.
   Но задание устроено так, что за один промпт оно не сдаётся.
   Баллы сосредоточены там, где нужен запущенный стенд и ваши собственные
   измерения. Если вы сдадите то, что LLM выдала с первого раза, вы получите
   примерно треть баллов.
3. **При обнаружении списывания** (одинаковый код в двух репозиториях без
   указания внешнего источника) оценка выставляется команде, чей коммит с

5. **Для старта работы из первого ДЗ нужны**:
четыре базы PostgreSQL, генератор синтетических данных, схема `contract` и возможность подключить
Debezium к лидеру каждой базы. Если нужно доработать источник, добавьте
миграцию в свой репозиторий.

## Формулировка

В ДЗ №1 вы спроектировали четыре независимых источника аптечной сети.

Теперь соберите детальный слой хранилища (DDS) для продаж, закупок и
движений партий. Аналитик должен уметь найти конкретную партию по
позиции чека, посмотреть предыдущую цену товара и узнать, сколько времени
партия ехала из распределительного центра в аптеку. Из DDS в ДЗ №3 будут
строиться витрины закупок и складской логистики.

## Задача

### Что должно работать в вашей сдаче

После запуска стенда и завершения начальной загрузки запрос к
`contract_dwh.v_sale_line` возвращает позиции чеков из ДЗ №1.
Чекер добавляет новую порцию в источники, ждёт её появления в Kafka
и raw, затем запускает загрузку DDS. Тот же запрос теперь возвращает
и новые позиции. Повтор загрузки этой порции сохраняет строки и версии
истории без дублей.

**Вам выдаются** `hw02_check.py`, контракт `hw02_contract.yaml`, пример
манифеста и [протокол чекера](checker_protocol.md).
**Вы пишете** Compose с автоматическим начальным наполнением, код доставки
в raw, таблицы и представления DDS и две команды:

| Команда в `hw02_submission.yaml` | Пример файла | Что делает ваш код |
|---|---|---|
| `commands.load` | `./scripts/load_dds` | Читает порцию из raw и загружает DDS. Запускается при старте стенда и по вызову чекера. См. шаг 3. |
| `commands.fixture` | `./scripts/check_fixture` | Записывает небольшие тестовые изменения в PostgreSQL. Эту команду вы реализуете в шаге 4. |

После реализации запустите из корня своего репозитория:

```bash
docker compose up -d
# Дождитесь завершения начальной загрузки по признаку из вашего README.
python /path/to/student_kit/hw02_check.py --submission ./hw02_submission.yaml --scenario
```

Вместо `/path/to/student_kit` укажите путь к скачанному комплекту.
Установка зависимостей и настройка подключений описаны в
[протоколе чекера](checker_protocol.md#запуск). Чекер сам вызовет обе
ваши команды в нужном порядке.

### 1. Спроектируйте DDS

Выберите **dimensional modeling, Data Vault или Anchor Modeling**.
**Создайте таблицы в схеме DDS по выбранной модели и записывайте
результат обработки raw именно в эти таблицы.** Для проверки создайте
отдельные SQL-представления (`VIEW`) из `hw02_contract.yaml`.
Бизнес-представления должны читать заполненные таблицы DDS.

| Движок | Куда загрузчик записывает данные DDS | Где чекер ожидает представления |
|---|---|---|
| Greenplum | Таблицы в схеме `dwh_detailed` | Схема `contract_dwh` в той же базе |
| StarRocks | Таблицы в базе `dwh_detailed` | База `contract_dwh` в `default_catalog` |
| Trino + Iceberg | Таблицы Iceberg в схеме `dwh_detailed` с файлами в S3/MinIO | Схема `contract_dwh` в том же каталоге Iceberg, который указан в манифесте |

Подготовьте ER-диаграмму детального слоя.

Один товар, одна партия или одна аптека должны быть представлены как общая
бизнес-сущность. Например, товар из каталога, товар в позиции чека и товар
в строке закупки связываются по `sku`. У товара может быть несколько
исторических версий. Доработайте карту склейки из ДЗ №1 и покажите, какие
физические таблицы источника, топики и таблицы DDS участвуют в загрузке.

| Что доступно через `contract_dwh` | Что означает одна строка |
|---|---|
| `v_sale_line` | Одна позиция чека продажи или возврата. Ключ — `(receipt_bk, line_no)`. Для возврата доступны исходный чек и признак `doc_type`. Сумма хранится со знаком источника. |
| `v_purchase_line` | Одна позиция заказа поставщику. Ключ — `(purchase_bk, line_no)`. |
| `v_movement` | Одно перемещение партии. Ключ — `movement_bk`. Доступны обе локации и время отгрузки и приёмки, если они известны в источнике. |
| `v_sku`, `v_customer`, `v_pharmacy`, `v_batch`, `v_supplier`, `v_distribution_center` | Один доступный товар, клиент, аптека, партия, поставщик или РЦ на бизнес-ключ. |
| `v_sku_history`, `v_price_history` | Одна версия атрибутов товара или одна версия цены для конкретной области действия. |

Для SKU храните изменения названия, категории и признака Rx.
Если для атрибута был доступен только текущий срез, начните его историю
с первого снимка. Для истории SKU и цены используйте полуоткрытые
интервалы `[valid_from, valid_to)` без пересечений. `NULL` в конце
интервала означает открытую версию.

Имена, телефоны, электронную почту и другие контактные данные клиентов
оставьте в CRM (добавьте их в исключения на уровне Debezium).
После soft delete клиент исчезает из `v_customer`, а в
строках его чеков `customer_bk` становится `NULL`. Если клиент был
получателем складского движения, в этом движении скрывается `dst_bk`.
Строки чеков, суммы и движения сохраняются. В этом задании можно
пропустить способы оплаты чеков, карты лояльности и текущие остатки.

В `hw02_contract.yaml` указаны имена представлений, колонки и ключи.
Внутренние имена таблиц и SQL представлений выбираете вы. При выборе имен
таблиц руководствуйтесь принятым для вашей модели неймингом: fact_*/dim_* для dimensional
modelling, hub_*/sat_*/elink_*/tlink_* для data vault и anc_*, tie_*, attr_* для anchor
modelling.

### 2. Поднимите OLAP и доставьте данные в raw-слой

Выберите **Greenplum, StarRocks или S3/MinIO + Trino + Iceberg (бонус)**.
**На чистом стенде из корня репозитория всё должно запускаться одной
командой `docker compose up -d`.** Compose поднимает четыре базы ДЗ №1 и
сервисы ДЗ №2, автоматически применяет миграции, запускает генератор ДЗ №1,
настраивает доставку в raw и выполняет первую загрузку DDS после поступления
начальных данных в raw. Отдельных ручных команд для этих шагов быть не должно.
В README укажите переменные окружения и как проверить, что начальная
загрузка завершилась. Для lakehouse укажите версию Trino и каталог Iceberg.

Настройте репликацию `PostgreSQL → Debezium → Kafka → raw` для всех четырёх
баз. У каждой базы свой коннектор, слот и префикс топиков. Debezium читает
физические таблицы, а представления из контракта ДЗ №1 используются ТОЛЬКО для сверки.
В raw должны поступать записи начального снимка и последующие изменения.
На MPP храните raw в выбранной СУБД (GreenPlum/StarRocks). Для lakehouse храните raw в S3
и обеспечьте его чтение через Trino.

Сохраняйте полезную нагрузку для переобработки, код источника, таблицу,
ключ исходной записи, операцию, Kafka topic/partition/offset и время
приёма. Через `contract_dwh.v_cdc_events` покажите эти технические поля.
Операция `r` обозначает запись начального снимка.

### 3. Реализуйте наполнение DDS

Выберите, как вы будете наполнять DDS.
Это может быть последовательный запуск SQL-скриптов (с общей входной точкой) или dbt.
Укажите эту команду в `commands.load`. Например, если вы назвали её
`./scripts/load_dds`, она должна поддерживать три вызова:

| Вызов | Что делает загрузчик |
|---|---|
| `./scripts/load_dds` | Читает новую порцию из raw и сам создаёт её идентификатор. Этот вызов можно использовать для первой загрузки в Compose. |
| `./scripts/load_dds --batch-id ID` | Загружает новую порцию и сохраняет переданный чекером ID. |
| `./scripts/load_dds --batch-id ID --replay` | Читает заново сохранённый диапазон той же порции и применяет его к DDS без дублей. |

Первый запуск наполняет DDS. После этого обрабатывайте новые события из raw и меняйте
только затронутые записи или ограниченные партиции. Сохранённая позиция
обработки должна продвигаться после успешной загрузки. Переигрывание
того же входа оставляет те же факты и версии истории.

- `batch_id` — идентификатор порции входных событий. При обычном запуске
  для новой порции его создаёт ваш загрузчик, например генерирует UUID.
  При самопроверке чекер сам создаёт идентификатор и передаёт его загрузчику
  через `--batch-id`. Если аргумент передан, используйте это значение.
- В `contract_dwh.v_load_batches` показывайте одну строку на `batch_id`:
  диапазоны Kafka offsets и статус загрузки. При повторе загрузчик получает
  тот же `batch_id` и заново обрабатывает сохранённые диапазоны.
- Для строки или версии DDS должна быть доступна связь с источником и
  `batch_id`. Храните её в таблицах DDS или в технической таблице.
  Для составного факта укажите основной источник и происхождение полей
  из связанных сервисов в карте склейки.

Чекер дождётся поступления всей тестовой порции в raw перед запуском
DDS. Студенческий интерфейс проверки описан в `checker_protocol.md`.

**Не забудьте про сегментацию и партиционирование таблиц DDS.**
Для Greenplum укажите ключ распределения по сегментам, для StarRocks —
ключ и способ распределения данных по бакетам. Для крупных таблиц
обоснуйте выбор ключа партиционирования. В Iceberg опишите
партиционирование таблиц. Если конкретную таблицу оставили без партиций,
объясните почему.

Приложите три ADR с рассмотренной альтернативой и причиной выбора:
модель и назначение строк, физическая организация таблиц, обработка
истории и повторного запуска.

В журнал прогона приложите команды и сырой вывод для начальной загрузки,
новой порции и повтора. Покажите границы входа, число обработанных
событий, что изменилось в DDS и сколько заняла операция.

### 4. Реализуйте тестовую догенерацию для чекера

Напишите команду, которая вносит небольшую порцию тестовых данных в
физические таблицы вашего ДЗ №1. Укажите её в `commands.fixture`.
`./scripts/check_fixture` — пример имени файла. Можно использовать
ваш генератор ДЗ №1, добавив в него нужные режимы или обёртку.

| Вызов | Что записывает команда |
|---|---|
| `./scripts/check_fixture delta` | Создаёт связанные записи в четырёх базах. Клиента, товар с ценой, чек с этим клиентом и товаром, закупку и движение партии. |
| `./scripts/check_fixture history` | Меняет название и цену тестового товара. Ранее созданный чек сохраняет исходные данные. |
| `./scripts/check_fixture privacy` | Помечает тестового клиента удалённым в CRM. |

Чекер передаёт параметры шага как JSON на стандартный ввод.
После коммита выведите один JSON на стандартный вывод. Для `delta`
укажите ключи добавленных записей и ожидаемые события Kafka. Для
`history` и `privacy` достаточно списка событий. Ваш скрипт пишет
в PostgreSQL. События публикует Debezium, а загрузку DDS запускает
чекер отдельной командой. Точные поля JSON и пример вызова есть в
[протоколе чекера](checker_protocol.md#интерфейс-команды-записи-тестовых-данных).

## Как это будет проверяться?

Сначала преподаватель выполняет `docker compose up -d` и ждёт
завершения автоматической начальной загрузки. Обычный запуск чекера
читает представления и сверяет исходные данные с DDS. Полный сценарий
добавляет тестовые данные в источники, сам читает Kafka и raw, запускает
загрузку и проверяет результат. Этот режим запускается на отдельном
учебном стенде. Подробности и команды — в `checker_protocol.md`.

Чекер выдаёт до 13 баллов автоматически. Диаграмма, запуск, физическая
модель, код загрузки, журнал и бонусы проверяются вручную. Если один
этап заблокирован, преподаватель учитывает уже подтверждённые независимые
этапы. На выборочной защите покажите, как одна тестовая запись прошла
от PostgreSQL через raw до DDS.
