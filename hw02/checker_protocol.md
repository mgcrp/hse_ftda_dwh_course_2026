# Протокол самопроверки ДЗ №2

## Запуск

Требуется Python 3.10+. Скопируйте
`hw02_submission.example.yaml` в корень своей работы как
`hw02_submission.yaml`. Заполните переменные окружения из манифеста.
Из корня проекта выполните `docker compose up -d`. Дождитесь
завершения автоматической начальной загрузки по признаку из README.
Compose сам применяет миграции, генерирует данные ДЗ №1 и загружает
первую порцию через raw в DDS. Пока работает чекер, следующие порции
должны загружаться только по его команде.

```bash
python -m pip install -r requirements.txt
python hw02_check.py --self-test
python hw02_check.py --submission ./hw02_submission.yaml --json static.json
python hw02_check.py --submission ./hw02_submission.yaml --scenario --json scenario.json
```

Первый прогон со сдачей только читает данные. `--scenario` выполняет
команды из манифеста, создаёт новые записи и обезличивает тестового
клиента. Используйте отдельный учебный стенд. Для повторного полного
прогона восстановите начальное состояние, если генератор допускает
только фиксированный набор тестовых ключей. По умолчанию тайм-аут
отдельного запроса, команды или ожидания — 90 секунд. Его можно увеличить
через `--timeout`.

## Доступ к данным

- Для PostgreSQL укажите прямой SQL-адрес источника. Достаточно доступа
  на чтение схемы `contract` ДЗ №1. Подключение для записи использует
  ваш скрипт тестовых данных.
- В Greenplum и Trino `contract_dwh` — схема. В StarRocks это база
  в `default_catalog`. Пользователь чекера должен видеть представления
  через `information_schema.views` и колонки через
  `information_schema.columns`. Дайте этому пользователю права на
  чтение контракта.
- Имя каталога, схемы и имена SQL-объектов контракта пишутся строчными
  латинскими буквами, цифрами и подчёркиваниями. `timestamp` без часового
  пояса и `datetime` в контракте интерпретируются как UTC. Выберите
  точность, которая сохраняет время источника. Денежные поля имеют
  тип `DECIMAL` или `NUMERIC`. В StarRocks для флага допустим `TINYINT`
  со значениями 0 и 1.
- Для учебного прогона откройте Kafka listener для чекера. Ключ и
  envelope Debezium передаются в JSON. Чекер принимает и обычный JSON,
  и формат Kafka Connect с полями `schema` и `payload`.
  У события должны быть `op` и `source.schema` / `source.table`.
  Для проверяемых топиков сохраните исходный envelope. Все топики из
  манифеста должны существовать до сценария. Топики таблиц, которые
  остаются пустыми после snapshot, можно создать при запуске стенда.
- Для lakehouse используйте каталог Iceberg с проверенной поддержкой
  представлений. `v_cdc_events` в Trino должен читать данные из raw в S3.
  Для остальных движков это представление над raw в выбранном движке.

## Сверка начальной загрузки DDS

После начального наполнения запустите из корня своей работы:

```bash
python /path/to/student_kit/hw02_check.py --submission ./hw02_submission.yaml --json static.json
```

Замените `/path/to/student_kit` путём к скачанному комплекту. Чекер
читает исходные представления `contract` в PostgreSQL и результат из
`contract_dwh` на выбранном OLAP-движке. Те же проверки запускаются
в начале `--scenario`, до тестовых изменений.

| Пункт в отчёте | Что сверяется с ДЗ №1 | Ключ и проверка связей |
|---|---|---|
| `dds.sales` | `contract_dwh.v_sale_line` с позициями `contract.v_receipt_line` и полями заголовка `contract.v_receipt` из POS. | `(receipt_bk, line_no)`. Проверяются товар, его соответствие партии, аптека, клиент при наличии и исходная продажа для возврата. |
| `dds.purchases` | `contract_dwh.v_purchase_line` с `contract.v_purchase_line` из WMS. | `(purchase_bk, line_no)`. Проверяются товар, партия при наличии, поставщик и РЦ. |
| `dds.movements` | `contract_dwh.v_movement` с `contract.v_movement` из WMS. | `movement_bk`. Проверяются товар, его соответствие партии и ссылки на локации по их типу. |
| `dds.dimensions` | `v_customer` из CRM, `v_sku` из каталога, `v_pharmacy` из POS, `v_batch`, `v_supplier` и `v_distribution_center` из WMS. Каждое исходное представление сверяется с одноимённым в `contract_dwh`. | По бизнес-ключу каждой сущности. Для каждой партии проверяется ссылка на товар. |

Для каждого представления чекер проверяет минимальный объём источника
по `min_rows` в `hw02_contract.yaml`, обязательные поля и типы,
отсутствие дублей по ключу, затем сравнивает **все ключи и значения
колонок контракта**. Лишняя строка, пропущенная строка или несовпадение
значения приводят к ошибке. Например, для `dds.sales` в источнике нужно
как минимум 60 000 позиций, а в DDS должна совпасть каждая позиция.

За каждый зелёный пункт `dds.*` начисляется 1 балл. Все шесть
справочников проверяются одной группой. В отчёте выводится причина
первой ошибки по каждой группе. История SKU и цен и инкрементальная
загрузка имеют отдельные пункты оценки в `--scenario`.

## Интерфейс команды записи тестовых данных

Реализуйте эту команду в своём репозитории. `./scripts/check_fixture` —
пример пути из манифеста. Команда зависит от ваших таблиц и ограничений
в ДЗ №1. Можно переиспользовать код генератора ДЗ №1 и добавить обёртку
с интерфейсом ниже. В `commands.fixture` укажите путь или команду
интерпретатора, например `[python3, scripts/check_fixture.py]`.

Чекер запускает `commands.fixture <шаг>`, передаёт JSON в stdin и
читает один JSON-объект из stdout. Журнал команды пишите в stderr.
Команда завершается после коммитов в источниках. Она пишет только в
PostgreSQL и соблюдает ограничения схемы ДЗ №1.

| Шаг | Запрос чекера | Что записать |
|---|---|---|
| `delta` | `{"batch_id":"<идентификатор порции от чекера>"}` | Добавить клиента, SKU с открытой ценой, чек с этим клиентом и SKU, строку закупки и движение для этого SKU. Добавить зависимые записи, если они нужны для целостности. Выдать новые ключи в ответе. Удобно расширить ваш генератор ДЗ №1 небольшим сценарием с нужными связями. |
| `history` | `batch_id`, объект `keys` из `delta`, строка `sku_name` | Поменять название указанного SKU на переданное. Закрыть действующую цену и добавить отличающуюся цену для того же SKU и области действия. Существующий чек оставить прежним. |
| `privacy` | `batch_id`, объект `keys` из `delta` | Выполнить soft delete указанного клиента так же, как в ДЗ №1. |

Скрипт может использовать `batch_id` для получения уникальных тестовых
ключей. Сохранять `batch_id` в таблицах источников не требуется.

После реализации можно проверить команду вручную на учебном стенде:

```bash
printf '%s\n' '{"batch_id":"manual-demo-001"}' | ./scripts/check_fixture delta
```

Пример формы ответа на `delta`:

```json
{
  "keys": {
    "customer_bk": "CUST-920001",
    "sku": "SKU-920001",
    "receipt_bk": "RCPT-20261201-920001",
    "purchase_bk": "PO-920001",
    "movement_bk": "MOV-920001"
  },
  "events": [
    {"topic": "crm.public.customer", "key": {"customer_id": 920001}, "op": "c"},
    {"topic": "catalog.public.sku", "key": {"sku_id": 920001}, "op": "c"}
  ]
}
```

В примере показаны две записи из списка. В реальном ответе перечислите
**все CDC-события этого шага, которые нужны для загрузки DDS**. Например,
для отдельной таблицы позиций чека нужны события по заголовку и позиции.
События зависимых записей также перечисляются. В `history` и `privacy`
достаточно поля `events`. В `key` передайте объект или скаляр из ключа
Kafka после снятия обёртки Kafka Connect. Например, для таблицы с
числовым PK ключ может содержать `customer_id`, а `customer_bk` при этом
остаётся бизнес-ключом. Допустимые значения `op` для шагов — `c`,
`u`, `d`. Kafka tombstone не включается.

Чекер фиксирует конец партиций до записи и читает от этой позиции своей
группой без коммита offsets. Затем он ищет те же сообщения в
`v_cdc_events`. В `event_key` храните тот же ключ как JSON-текст.
`source_system` принимает значения `crm`, `catalog`, `pos`, `wms`.
`source_table` имеет формат `schema.table`. Повтор доставки одного
Kafka-сообщения должен давать одну запись в диагностическом
представлении по `(topic, partition_id, kafka_offset)`.

## Интерфейс команды загрузки

В обычном режиме без `--batch-id` загрузчик сам создаёт идентификатор
новой порции, например UUID. Это относится и к первой загрузке при
старте Compose. В тестовом режиме чекер создаёт `batch_id` и запускает
`commands.load --batch-id ID`, когда ожидаемые события шага видны в raw.
Сохраните переданный идентификатор вместе с диапазонами порции.
Команда возвращает код 0 после завершения загрузки.

При `commands.load --batch-id ID --replay` загрузчик по этому же
идентификатору находит сохранённые диапазоны, читает их заново и
применяет ту же логику записи. Успешный повтор не меняет границы
порции, бизнес-строки или историю.

В `v_load_batches.offsets_json` храните JSON-массив непустых
полуоткрытых диапазонов Kafka offsets, по одному на topic/partition.
Например, `[{"topic":"crm.public.customer","partition":0,"start_offset":15,"end_offset":18}]`
означает offsets 15, 16 и 17. У завершённой порции статус `success`.
В представлении должна быть ровно одна строка на `batch_id`, в том
числе после повтора. Число обработанных событий и время выполнения
приложите в журнале прогона.

## Отчёт и ограничения

`pass` начисляет баллы, `fail` означает 0 по проверенному пункту,
`blocked` указывает недоступный зависимый шаг, `skipped` означает
выключенный сценарий, `manual` оставляет решение преподавателю.
Автоматическая оценка — до 13 из 20. При сбое автоматической проверки
чекер возвращает код 1. JSON содержит статус, баллы и причину для каждого
пункта. При проверке преподаватель также смотрит SQL или код и журнал,
чтобы отличить обработку дельты от полного пересчёта.
