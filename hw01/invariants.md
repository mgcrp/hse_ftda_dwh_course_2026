# Обязательные инварианты источников — ДЗ №1

Инвариант — утверждение о данных, которое **не может быть нарушено физически**.
Не «приложение не должно такое писать», а «база не даст это записать».

К каждому инварианту ниже вы обязаны:

1. реализовать его средствами PostgreSQL — `CHECK`, `UNIQUE`,
   partial `UNIQUE INDEX`, `EXCLUDE`, `FOREIGN KEY`, `CONSTRAINT TRIGGER`;
2. написать **негативный тест** — SQL-файл, который пытается нарушить
   инвариант и обязан завершиться ошибкой;
3. указать инвариант, файл и ожидаемый `SQLSTATE` в `hw01_submission.yaml`.

Чекер выполняет каждый файл в отдельной транзакции, пытается сделать
`COMMIT`, требует ошибку с заявленным вами кодом и убеждается, что после
откатa количество строк не изменилось.

## Правила написания негативных тестов

* Тест **самодостаточен**: сам создаёт всё, что ему нужно (при необходимости —
  вспомогательного клиента, SKU, партию), и падает на последней операции.
* Тест **не ослабляет схему**. Запрещены и автоматически детектируются:
  `ALTER TABLE ... DROP CONSTRAINT`, `ALTER TABLE ... DISABLE TRIGGER`,
  `SET CONSTRAINTS ... IMMEDIATE`, `SET session_replication_role`,
  `DROP INDEX`, `ALTER ... NOT VALID`, `ALTER TABLE ... ALTER COLUMN ... DROP NOT NULL`.
  Тест с такой строкой считается непройденным.
* `ROLLBACK`/`COMMIT` внутри файла писать не надо — транзакцией управляет чекер.
* В файле может быть **несколько операторов** — чекер выполняет их одним
  запросом и берёт результат последнего. Для положительных тестов это важно:
  data-modifying CTE (`WITH upd AS (UPDATE ...) SELECT ... FROM таблица`)
  не увидит своих же изменений — CTE работают на одном снимке данных.
  Пишите `UPDATE ...;` и отдельным оператором `SELECT ... AS ok;`.
* Один файл — один инвариант.
* Ожидаемый `SQLSTATE` вы определяете экспериментально, запустив тест.
  Угадать его по документации можно, но проверить — обязательно.

Подсказка по кодам:

| код | когда |
|-----|-------|
| `23505` | `unique_violation` — UNIQUE / PRIMARY KEY / partial unique index |
| `23514` | `check_violation` — `CHECK` |
| `23503` | `foreign_key_violation` |
| `23502` | `not_null_violation` |
| `23P01` | `exclusion_violation` — `EXCLUDE USING gist` |
| `P0001` | `raise_exception` — ваш `RAISE EXCEPTION` в триггере |
| `22003` | `numeric_value_out_of_range` |

Свой код в `RAISE EXCEPTION ... USING ERRCODE` тоже допустим — тогда
указывайте его.

## Негативные тесты (12 обязательных)

### I1. Business key уникален

Два разных объекта не могут иметь один business key.
Проверяется на любой сущности со BK — укажите, на какой.

Допустимые коды: `23505`

### I2. Business key неизменяем

`UPDATE`, меняющий BK существующей записи, обязан упасть.
BK — то, на что будет опираться DWH; если он поедет, поедет всё.

Допустимые коды: `P0001`, `23505`, `0A000`, свой код из `ERRCODE`

### I3. Сумма документа совпадает с суммой позиций

Нельзя оставить кассовый документ в состоянии, где `total_amount`
не равен сумме `line_amount` его позиций.

Это **не реализуется обычным `CHECK`** — ограничение затрагивает две
таблицы и обязано проверяться в конце транзакции. Нужен
`CONSTRAINT TRIGGER ... DEFERRABLE INITIALLY DEFERRED`.
Тест должен вставить документ и позиции с расхождением; ошибка прилетит
на `COMMIT`, и это нормально.

Допустимые коды: `P0001`, `23514`, свой код из `ERRCODE`

### I4. Арифметика и знаки в позиции документа

Одновременно: `quantity > 0`, `unit_price >= 0`, `line_discount >= 0`,
`line_discount <= quantity * unit_price`,
`line_amount = quantity * unit_price - line_discount`.

Негативный тест — на любое одно из условий (какое, укажите в манифесте).

Допустимые коды: `23514`

### I5. Интервалы действия цены не пересекаются

Для одной комбинации (SKU, область действия) не может существовать
двух версий цены с пересекающимися интервалами
`[valid_from, valid_to)`.

Обычным `UNIQUE` это не выражается. Смотрите в сторону
`CREATE EXTENSION btree_gist` и
`EXCLUDE USING gist (... WITH =, tstzrange(valid_from, valid_to, '[)') WITH &&)`.

Допустимые коды: `23P01`, `P0001`

### I6. Ровно одна текущая версия

У сущности с историей не может быть двух записей с `is_current = true`
на один ключ. Дешёвое решение — partial unique index.

Допустимые коды: `23505`

### I7. Остаток не может стать отрицательным

Нельзя привести остаток партии в локации к отрицательному значению —
ни вставкой, ни списанием больше, чем есть.

Способ хранения остатка вы выбираете сами (материализованная таблица
с триггерами или вычисление из журнала). Инвариант обязан держаться
при любом выборе.

Допустимые коды: `23514`, `P0001`, свой код из `ERRCODE`

### I8. Нельзя продать партию с истёкшим сроком годности

Позиция кассового документа с датой документа позже `expiry_date`
партии не должна записываться.

Допустимые коды: `P0001`, `23514`, свой код из `ERRCODE`

### I9. Нельзя принять на склад партию с истёкшим сроком годности

Приёмка партии, срок которой уже истёк на момент приёмки, отклоняется.

Допустимые коды: `P0001`, `23514`, свой код из `ERRCODE`

### I10. Рецептурный препарат не отпускается без рецепта

Позиция с `is_rx_snapshot = true` не может попасть в документ,
у которого не указан рецепт.

Обратите внимание: признак рецептурности живёт в другом сервисе
(`catalog_service`), а ограничение нужно здесь. Из этого следует
конкретное требование к вашей модели — какое, решайте сами,
и запишите решение в ADR.

Допустимые коды: `23514`, `P0001`, свой код из `ERRCODE`

### I11. Возврат не превышает проданное

Нельзя вернуть по документу-возврату больше единиц SKU, чем было
продано в родительском документе (с учётом ранее оформленных возвратов).

Допустимые коды: `P0001`, `23514`, свой код из `ERRCODE`

### I12. Сумма оплат совпадает с суммой документа

Документ не может остаться оплаченным частично или с перебором.
Как и I3 — проверка в конце транзакции.

Допустимые коды: `P0001`, `23514`, свой код из `ERRCODE`

## Положительные тесты (2 обязательных)

Эти тесты, наоборот, обязаны **успешно выполниться** и вернуть один
столбец `ok` со значением `true` (одна строка). Транзакцию чекер
откатывает.

### P1. `updated_at` обновляется автоматически

Выполните `UPDATE` любой строки, не указывая `updated_at` явно,
и убедитесь, что значение изменилось.

Пример структуры теста:

```sql
-- tests/invariants/P1_updated_at.sql
WITH before AS (
    SELECT sku_id, updated_at FROM catalog.sku ORDER BY sku_id LIMIT 1
), upd AS (
    UPDATE catalog.sku s SET sku_name = sku_name || ' (test)'
     WHERE s.sku_id = (SELECT sku_id FROM before)
    RETURNING s.sku_id, s.updated_at
)
SELECT (upd.updated_at > before.updated_at) AS ok
FROM upd JOIN before USING (sku_id);
```

(имена таблиц — ваши, это только форма)

### P2. Soft delete скрывает клиента из контракта

Помеченный удалённым клиент исчезает из `contract.v_customer`,
при этом физически строка остаётся, а персональные контакты обнулены
или обезличены.

Тест обязан вернуть `ok = true`, проверив все три факта.
