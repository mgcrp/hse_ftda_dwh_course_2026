# Демо 3. PgBouncer — пул соединений

**Вопрос, на который отвечает демо:** почему базу нельзя просто «открыть всем»
и что даёт прослойка между приложением и PostgreSQL.

## Что внутри

| контейнер    | что это                                                               |
|--------------|-----------------------------------------------------------------------|
| `postgres`   | PostgreSQL 18, специально зажатый: `max_connections = 20`             |
| `pgbouncer`  | PgBouncer 1.25, `pool_mode = transaction`, `default_pool_size = 5`    |
| `watcher`    | живой дашборд для проектора                                           |
| `pg_cli`     | контейнер с `psql` и `pgbench`, из него запускаются сценарии          |

## Запуск

```bash
docker compose up -d
```

Открываем **два окна терминала** и раскидываем их по экрану:

```bash
# окно 1 — дашборд, он должен быть виден всё демо
docker compose logs -f watcher
```

```bash
# окно 2 — сценарии
docker compose run --rm pg_cli /scripts/01_flood.sh direct
```

Дашборд показывает две колонки, и весь семинар — про разницу между ними:

```
           |      PgBouncer (пул)        |   PostgreSQL (реальность)
  время    | clients  waiting  servers   |  backends   max_conn
-----------+-----------------------------+-----------------------
  12:01:03 |      45       40        5   |         5         20
```

### Ломаем базу через спам запросами

```bash
docker compose run --rm pg_cli /scripts/01_flood.sh direct
```

50 клиентов идут напрямую в PostgreSQL. Ожидаемый результат:

```
 ПОДКЛЮЧИЛИСЬ: 17 / 50
 ОТВАЛИЛИСЬ:   33 / 50
 Типичные ошибки:
    FATAL:  sorry, too many clients already
    FATAL:  remaining connection slots are reserved for roles with the SUPERUSER attribute
```

**Мысль вслух:** `max_connections` — это не «сколько клиентов выдержит база».
Каждый коннект в PostgreSQL — это **отдельный процесс ОС** со своим `work_mem`.
Поэтому `max_connections = 5000` не решение: база просто умрёт по памяти
и по контекстным переключениям.

### Тот же наплыв через пул

```bash
docker compose run --rm pg_cli /scripts/01_flood.sh pooled
```

```
 ПОДКЛЮЧИЛИСЬ: 50 / 50
 ОТВАЛИЛИСЬ:   0 / 50
```

На дашборде в этот момент: `clients ≈ 50`, `waiting ≈ 45`, `servers = 5`,
`backends = 5`. Пятьдесят клиентов — пять процессов в базе.

**Честная оговорка, которую важно проговорить:** пул не создал мощности из
воздуха. Сравните `ВРЕМЯ` в двух прогонах — во втором оно больше. PgBouncer
обменял *ошибки* на *ожидание*. Это почти всегда хороший обмен, но это обмен.

### Сколько стоит подключение

```bash
docker compose run --rm pg_cli /scripts/02_bench.sh
```

`pgbench -C` переподключается на каждую транзакцию — так ведут себя
короткоживущие воркеры, cron-скрипты, serverless-функции, ноутбуки аналитиков.

```
--- НАПРЯМУЮ ---     tps = 135
--- ЧЕРЕЗ PgBouncer --- tps = 248
```

Почти двукратная разница — это цена `fork()` бэкенда и аутентификации.
С TLS разрыв ещё больше.

### Чем мы за это платим

```bash
docker compose run --rm pg_cli /scripts/03_session_state.sh
```

Скрипт наглядно показывает: в `transaction` режиме «одна сессия» клиента
может по факту оказаться на разных серверных процессах. `pid` бэкенда
меняется, временная таблица исчезает, `statement_timeout` сбрасывается.

Что ломается в transaction pooling:

* `TEMP TABLE`
* `SET` / `RESET` (кроме `SET LOCAL` внутри транзакции)
* advisory-локи уровня сессии
* `LISTEN` / `NOTIFY`
* курсоры `WITH HOLD`
* prepared statements — до PgBouncer 1.21 не работали вовсе, сейчас лечатся
  параметром `max_prepared_statements`

*Нюанс:* `application_name`, `client_encoding`, `datestyle`, `timezone` и
`standard_conforming_strings` PgBouncer отслеживает сам и переигрывает на новом
серверном коннекте — поэтому в демо мы смотрим на `statement_timeout`,
который он не отслеживает.

### Акт 5. Пул как инструмент отказоустойчивости (4 мин)

```bash
docker compose run --rm pg_cli /scripts/04_pause_resume.sh
```

Скрипт запускает непрерывную нагрузку и делает `PAUSE shop`. Когда он попросит —
в соседнем окне:

```bash
docker compose restart postgres
```

Затем скрипт делает `RESUME shop` и печатает:

```
Успешных запросов: 104
Ошибок у клиентов: 0
```

Мы **перезапустили базу под нагрузкой, и ни один клиент не увидел ошибки.**
Ровно этим механизмом пользуются при switchover мастера и при минорных
апгрейдах PostgreSQL. Это мостик к Демо 4 (Patroni): там `PAUSE`/`RESUME`
делает не человек, а автоматика.

## Админ-консоль PgBouncer

```bash
docker compose exec pgbouncer psql -h 127.0.0.1 -p 6432 -U postgres -d pgbouncer
```

Полезное:

```sql
SHOW POOLS;    -- клиенты/серверы по каждой паре (база, пользователь)
SHOW CLIENTS;  -- кто подключён к pgbouncer
SHOW SERVERS;  -- реальные коннекты в postgres
SHOW STATS;    -- запросы/секунда, среднее время ожидания
PAUSE  shop;
RESUME shop;
RECONNECT shop;
```

`maxwait` в `SHOW POOLS` — главная метрика для алертов. Если он стабильно
больше нуля, пул мал (или запросы слишком длинные).

## Как подбирать `default_pool_size`

Правило большого пальца: `pool_size ≈ (2 … 4) × количество ядер` для OLTP.
Больше — не быстрее: база всё равно выполняет параллельно столько работы,
сколько у неё ядер и дисков, остальное просто стоит в очереди внутри PostgreSQL,
где очередь дороже, чем в pgbouncer.

## Уборка

```bash
docker compose down -v
```

## Чего PgBouncer не делает

* не балансирует нагрузку между репликами (это HAProxy — Демо 4);
* не переключает мастера (это Patroni — Демо 4);
* не разделяет чтение и запись — маршрут выбирает приложение или прокси;
* не защищает от «тяжёлого» запроса, только от «многих» подключений.
